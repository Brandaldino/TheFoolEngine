# RenderGraph 资源管理重构开发记录（FBO 归 RenderGraph 管理）

## 日期
2026-08-27

## 目标
将渲染管线的 FBO（HDR/LDR/Bloom 等渲染目标）从 EditorLayer 外部持有，迁移到 RenderGraph 统一管理，实现单一资源体系 + 拓扑排序调度。

---

## 一、最终架构

### RenderGraph（单一 FBO 资源体系）
```cpp
class RenderGraph
{
public:
    TextureHandle CreateRenderTarget(const TextureDesc& desc, const char* name);
    Ref<FrameBuffer> GetRenderTarget(const TextureHandle& handle) const;
    Ref<Texture2D> GetTexture(const TextureHandle& handle) const;
    void Resize(uint32_t width, uint32_t height);
    void AddPass(Scope<Pass> pass);
    void Execute(RenderContext& context);
private:
    std::vector<uint32_t> TopologicalSort();
    std::vector<Scope<Pass>> m_Passes;
    std::vector<Ref<FrameBuffer>> m_FrameBuffers;  // 唯一资源体系
};
```

### 核心原则
1. **RenderGraph 只管理 FBO**：一套 `m_FrameBuffers` 数组，`handle.PoolIndex` = FBO 索引
2. **每个 pass 自包含 Bind/UnBind**：`Bind 输出 → 画 → UnBind 回默认 framebuffer`
3. **RAW + WAW 拓扑排序**：读依赖写（RAW）+ 写依赖写（WAW，按 AddPass 顺序）

### 后处理 Pass 化
- MainPass / ShadowPass / PointShadowPass / BloomExtractPass / BloomBlurPass / BloomCombinePass / ToneMappingPass
- 每个 pass 从 `ctx.RenderGraph` 拿资源，不持有 FBO

## 二、关键坑及解决

| # | 现象 | 根因 | 解决 |
|---|------|------|------|
| 1 | 两套资源体系并存 | `m_Pool`（旧纹理池）+ `m_FrameBuffers`（新 FBO）混用，PoolIndex 语义混乱 | 删掉 ResourcePool / CreateTexture / RegisterTexture，只留 FBO 体系 |
| 2 | 闪屏 + 纯黑（每帧 resize）| `m_ViewportSize` 是 float（小数），FBO 规格是 uint32（截断），`spec.Width != m_ViewportSize.x` 永远为真 → 每帧重建 FBO | 尺寸整数化，统一 resize 逻辑 |
| 3 | ImGui 画错地方 | `glBindFramebuffer(0)`（切回屏幕）藏在 `m_LDRFrameBuffer->UnBind()` 里，删 FBO 时误删 | 每个 pass 自己 UnBind 回默认 framebuffer |
| 4 | 后处理 pass 崩溃（空指针）| pass 还用 `ctx.ResourcePool->GetTexture`（已废弃空指针）| 改成 `ctx.RenderGraph->GetTexture(handle)` |
| 5 | WAW 依赖丢失 | 回退时拓扑排序只剩 RAW，多 pass 写同一资源时顺序错乱 | 恢复 WAW（lastWriter 映射）|
| 6 | MainPass 在 ShadowPass 前执行 | 阴影 FBO 外部管理，MainPass 没声明依赖阴影 | 阴影系统后续迁入 RG，或显式依赖 |

## 三、关键经验教训

1. **单一资源体系**：FBO 归 RG 管理后，`handle.PoolIndex` 只有一种语义（FBO 索引），彻底消除"两套索引"的混乱。

2. **`UnBind()` 的真实含义**：`OpenGLFrameBuffer::UnBind()` 内部是 `glBindFramebuffer(GL_FRAMEBUFFER, 0)`——**不是"解绑这个 FBO"，而是"切回默认 framebuffer（屏幕）"**。这是 ImGui 能正确渲染到屏幕的必要操作，删 FBO 时容易误删。

3. **resize 精度陷阱**：float 尺寸（ImGui 实时值）vs uint32 规格（FBO 截断）会导致 `!=` 永远为真 → 每帧 resize 死循环。必须整数化比较。

4. **WAW 依赖**：拓扑排序不能只有 RAW（读依赖写），还必须处理 WAW（写依赖写），否则多个 pass 写同一资源时顺序随机。

5. **ResourcePool 的定位**：FBO 是"长期资源"（跨帧持有，天然复用）；ResourcePool 是"临时资源池化"（用完就还）。当前引擎只有长期资源，故删 ResourcePool，但文件保留（将来 SSAO/中间纹理时再用）。
